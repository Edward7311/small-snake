# 《贪吃蛇》—— 功能与模块说明

## 一、项目概览

在 40 × 40 的网格地图上操控一条蛇。蛇持续朝当前方向前进，玩家可以转向；吃到食物后蛇身变长、分数加一，并且移动速度随分数逐步加快。撞到边界墙或撞到自己的身体即游戏结束。

地图共 40 × 40 = 1600 格，窗口尺寸 = 40 × 20 像素 + 四周 40 像素留白 + 36 像素信息栏，即 **880 × 916**。

整个项目的设计主线是一句话：

> **每加一个真实的游戏机制，就往里塞一个数据结构，再用实测数据证明它比朴素写法快。**

基础版贪吃蛇其实只有"蛇身用链表还是数组"这一个数据结构点，撑不起数据结构分析。所以项目刻意把游戏做复杂一点点，于是有了下面三处真实的数据结构战场。

---

## 二、模块划分总览

| 模块 | 文件 | 功能职责 | 采用的数据结构 | 核心复杂度 |
|---|---|---|---|---|
| 公共定义层 | `include/common.h` | 地图尺寸、坐标编码、返回值约定 | 一维整数坐标编码 | — |
| 蛇身模块 | `deque.h` / `deque.c` | 蛇身移动 | 双端队列（双向链表） | 头插尾删 O(1) |
| 碰撞检测模块 | `hashset.h` / `hashset.c` | 咬到自己检测 | 哈希集合（链地址法） | 查询平均 O(1) |
| 食物生成模块 | `foodpool.h` / `foodpool.c` | 随机生成食物 | 空闲格集合（数组 + 下标互指） | 取格 O(1)，永不重试 |
| 逻辑层 | `game.h` / `game.c` | 状态机、规则、三个结构的同步维护 | 状态机 + 三个结构 | — |
| 主循环 | `src/main.c` | 收键盘、固定步进、渲染、状态切换 | 时间戳累加计时 | — |
| 渲染层 | `render.h` / `render.cpp` | 只读地把状态画出来 | 双缓冲绘制 | — |
| 实验层 | `bench/bench.c`、`bench/test_logic.c` | 对比实验数据、逻辑自测 | 朴素实现 vs 优化实现对照 | — |

### 三处数据结构战场（速查）

| 游戏模块 | 朴素做法的问题 | 采用的数据结构 | 复杂度对比 |
|---|---|---|---|
| 蛇身移动 | 数组整体搬移，每步 O(n) | 双端队列（双向链表） | O(n) → O(1) |
| 咬到自己检测 | 遍历整个身体查找 O(n) | 哈希集合（链地址法） | O(n) → O(1) |
| 食物生成 | 随机取格、撞了重试，蛇越长越慢 | 空闲格集合（数组 + 下标互指 + 交换删除） | 期望上百次重试 → 恒定 1 次 |

## 三、各模块详解

### 3.1 公共定义层 `common.h` —— 坐标表示

这个模块本身没有复杂数据结构，但它定下了全项目最关键的一条约定：**二维坐标 `(x, y)` 压缩成一个整数** `pos = y * 40 + x`。

```c
typedef int Pos;

#define POS_MAKE(x, y)   ((y) * MAP_W + (x))
#define POS_X(p)         ((p) % MAP_W)
#define POS_Y(p)         ((p) / MAP_W)
#define POS_VALID(p)     ((p) >= 0 && (p) < POS_COUNT)
```

好处是这一个 `int` **同时**当三个角色用：

- 蛇身链表里存的值
- 哈希表的键
- 空闲格数组的下标（下标恰好等于格子编号，省掉一次映射）

三者共用同一种表示，就省掉了一层坐标映射——这正是最容易出隐蔽 bug 的地方。另外，一次整数比较就完成判等，比比较结构体快得多，也让哈希更简单。

模块里还统一了返回值约定，全项目通用：

```c
#define OK           0
#define ERR         (-1)
#define ERR_NOTFOUND (-2)
#define ERR_DUPLICATE (-3)
#define ERR_EMPTY    (-4)
```

需要返回多个值时，一律用"出参指针 + 返回状态码"，不使用全局变量。

### 3.2 蛇身模块 `deque` —— 双端队列（双向链表）

**功能**：维护蛇身每一节所在的格子。

**为什么用双端队列**：贪吃蛇每走一步只有两个动作——在头部插入一节、在尾部删除一节。

- 数组实现：头部插入要整体搬移，O(n)；或改用环形数组，但要固定长度上限。
- 双向链表：头尾插入/删除都是 O(1)，且长度不设上限。

**结构定义**：

```c
typedef struct DNode {
    Pos           value;    /* 该节所在的格子编号 */
    struct DNode *prev;
    struct DNode *next;
} DNode;

struct Deque {
    DNode *head;   /* 队头 —— 蛇头 */
    DNode *tail;   /* 队尾 —— 蛇尾 */
    int    size;   /* 元素个数，避免每次求长度都遍历一遍 */
};
```

**实现要点**：`size` 字段单独维护，防止求长度退化成 O(n)；所有边界情况（空队列、NULL 指针）显式处理。头插的写法值得一看：

```c
n->next = dq->head;
n->prev = NULL;
if (dq->head != NULL) dq->head->prev = n;
dq->head = n;
if (dq->tail == NULL) dq->tail = n;   /* 原本是空队列，新节点同时是队尾 */
```

**附带能力**：`push_back` / `pop_back` 让它可以直接当栈用，所以如果将来要做「撤销上一步」功能，不必再单独写一个 Stack 结构。

**保留的朴素接口**：`deque_contains()` 是 O(n) 的线性查找，正是"朴素版碰撞检测"的实现方式。它被保留下来专门给 `bench.c` 做对比实验，**绝不在优化版的每帧逻辑里调用**。

**复杂度**：push_front / push_back / pop_front / pop_back 全部 O(1)；contains / foreach 为 O(n)。每个节点的额外开销是 2 个指针。

### 3.3 碰撞检测模块 `hashset` —— 哈希集合（链地址法）

**功能**：判断"蛇头的新位置是否撞到自己身上"，本质是一次集合的成员查询。

**为什么用哈希集合**：

- 朴素做法：遍历整条蛇逐个比较，O(n)。蛇长 1000 时每帧就是 1000 次比较。
- 哈希集合：把格子编号直接哈希，平均 O(1)。

**结构定义**：

```c
typedef struct HNode {
    Pos           key;
    struct HNode *next;   /* 链地址法：冲突节点挂在同一个桶后面 */
} HNode;

struct HashSet {
    HNode **buckets;
    int     capacity;   /* 桶数 */
    int     size;       /* 元素个数 */
    HashSetStats stats; /* 运行期统计量，供对比实验用 */
};
```

**哈希函数（本模块最值得讲的部分）**：

格子编号 `pos = y * 40 + x`，相邻格子只差 1。如果直接写 `key % 桶数`，当桶数与 `MAP_W = 40` 有公因子时，**同一列的格子会被整列撞进同一个桶**，哈希表退化成链表。所以先用 splitmix 风格的乘法散列把低位差异放大到高位，再对桶数取模：

```c
unsigned int hs_hash(Pos key)
{
    unsigned int x = (unsigned int)key;
    x ^= x >> 16;  x *= 0x7feb352dU;
    x ^= x >> 15;  x *= 0x846ca68bU;
    x ^= x >> 16;
    return x;
}
```

**扩容策略**：装载因子超过 0.75（代码里写作 3/4）时桶数翻倍并重新散列，均摊插入仍是 O(1)。元素数不超过 1600（地图总格数），所以桶数不会无限增长。

**统计接口**：`hs_contains()` 每次调用都如实累加 `lookups`（查询次数）和 `probes`（探测到的桶/链表节点比较次数）。这两个计数器就是报告里"比较次数"那一列数据的来源，答辩被追问时站得住。

### 3.4 食物生成模块 `foodpool` —— 空闲格集合

**功能**：在所有空格中随机挑一格放食物。

**为什么不用朴素做法**：

- 朴素做法：随机取一个格子，如果上面有蛇就重试。蛇长占地图 10% 时平均试 1.1 次，没什么感觉；占 90% 时平均要试 10 次，占 99% 时要试近 100 次——**这正是长蛇卡顿的根源**。

**实现思路：数组 + 下标互指 + 交换删除**

```c
struct FoodPool {
    int *cells;   /* 前 count 个位置紧凑存放"当前空闲"的格子编号 */
    int *slot;    /* slot[格子编号] = 它在 cells 中的下标；不在则为 -1 */
    int  count;   /* 当前空闲格数量 */
    unsigned long long attempts;   /* 累计取格次数，供对比实验使用 */
};
```

三个操作：

1. **取食物**：在 `[0, count)` 里随机取一个下标，O(1)，永不重试。
2. **移除格子**：交换删除，把数组末尾元素填到被删的坑里，O(1)。
3. **归还格子**：追加到数组末尾，O(1)。

移除（蛇吃掉食物 / 蛇头占格）的全部操作就是几行：

```c
int i    = fp->slot[cell];
int last = fp->cells[fp->count - 1];
fp->cells[i]    = last;
fp->slot[last]  = i;
fp->count--;
fp->slot[cell]  = -1;
```

**空间**：`cells` 和 `slot` 都是长度 1600 的一维数组，与蛇长无关，开销极小。

**用法约定**（调用方必须维护好这组对应关系，否则空闲集会与实际地图失配）：

| 时机 | 调用 |
|---|---|
| 蛇吃掉食物 | 该格变成蛇身 → `fp_remove()` |
| 蛇尾离开某格 | 该格恢复空闲 → `fp_add()` |
| 开局 / 重开 | → `fp_reset()` |

> 备选方案：也可以用并查集维护"连续空闲区间"，思路不同但同样正确。若组内有人第一部分实现的是并查集，可以作为替代实现写进报告做对比。

### 3.5 逻辑层 `game` —— 三个结构的同步维护

**功能**：游戏规则、状态机，以及把上面三个结构粘在一起。

`Game` 结构体持有三个结构：

```c
struct Game {
    Deque     *body;       /* 蛇身：双端队列，存每一节的格子号，头插尾删 */
    Direction  dir;        /* 当前方向 */
    Pos        food;       /* 当前食物所在格子 */
    HashSet   *occupied;   /* 已占格：哈希集合，用于 O(1) 碰撞检测 */
    FoodPool  *pool;       /* 空闲格：用于 O(1) 生成食物 */
    GameState  state;      /* 四个状态之一 */
    int        score;      /* 分数 */
    GameStats  stats;      /* 本局统计量 */
};
```

**关键纪律：三个结构必须始终一致。** 同一份坐标数据同时喂给这三个结构，所以"占一格 / 让一格"这类操作统一走一个内部函数，避免漏改某一边：

```c
static int occupy_cell(Game *g, Pos cell)
{
    if (hs_insert(g->occupied, cell) != OK) return ERR;
    if (fp_remove(g->pool, cell)     != OK) return ERR;
    return OK;
}

static int release_cell(Game *g, Pos cell)
{
    if (hs_erase(g->occupied, cell) != OK) return ERR;
    if (fp_add(g->pool, cell)       != OK) return ERR;
    return OK;
}
```

**`game_update()` 里的两个易错细节**

其一，**操作顺序**：不吃食物时要**先让出蛇尾、再占新头**，否则走到当前尾格时会在哈希表里重复插入：

```c
deque_pop_back(g->body, &gone);
release_cell(g, gone);
deque_push_front(g->body, &new_head);
occupy_cell(g, new_head);
```

其二，**蛇尾例外**：如果这一步会吃到食物，蛇尾不动，撞到尾要算撞；不吃食物时蛇尾会让开，此时"撞到当前尾巴所在格"其实是安全的。代码里就是这一行：

```c
if (hit && !(!will_eat && new_head == tail)) {
    g->state = GS_OVER;
    return ERR;
}
```

**三层隔离（本项目最重要的一条设计决定）**

逻辑层完全不知道 EasyX 的存在。`game.c` 及其以下不出现任何绘图代码，也不 include `graphics.h`；渲染层拿着一个 `const Game *`，只能通过只读查询接口读数据画图，物理上改不了游戏状态。收益有三个：

1. `bench.c` 能在**不开窗口**的情况下跑几十万步，输出对比数据；
2. 将来把 EasyX 换成 Qt，只需要重写 `render.cpp`，游戏逻辑一行都不用动；
3. 逻辑层可以脱离图形环境做单元测试（`test_logic.c` 就是这么跑起来的）。

### 3.6 主循环 `main.c` —— 输入、计时、驱动

职责只有四件事：**收键盘、按固定间隔推进逻辑、渲染、处理状态切换**。游戏规则一律不写在这里，全部交给 `game.c`。

**计时：不用 `Sleep()` 控制速度。** `Sleep()` 会让整个线程停下来，消息循环和按键检测都跟着被阻塞，表现出来就是"按了键要等半秒才响应"。正确做法是用时间戳累加：

```c
now = GetTickCount64();
if (game_state(g) == GS_RUNNING && now - last_step_ms >= step_ms) {
    last_step_ms = now;
    game_update(g);
    /* ... 难度曲线 ... */
}
Sleep(1);   /* 每帧末尾只让出一点 CPU，避免把单核跑满 */
```

**输入：用 `GetAsyncKeyState()`，不用阻塞式 `getch()`。** 方向键每次读；空格和 `R` 这类不需要连发的键则用"本帧刚被按下"的判定：

```c
static int key_pressed_once(int vk, int *was_down)
{
    int now_down = (GetAsyncKeyState(vk) & 0x8000) ? 1 : 0;
    int fresh    = (now_down && !(*was_down));
    *was_down    = now_down;
    return fresh;
}
```

### 3.7 渲染层 `render.cpp` —— 只读地把状态画出来

**功能**：把 `const Game *` 里的数据画成画面。这是全项目**唯一**允许 `#include <graphics.h>` 的文件。

**为什么后缀是 `.cpp`**：EasyX 的 `graphics.h` 内含 `#error "EasyX is only for C++"`，不能用 C 编译器编译。所以 `render.c` 已改名为 `render.cpp`，工程里其余模块保持 `.c`。**因而所有头文件必须包 `extern "C"`**，否则 C++ 会对函数名做 name mangling，和 C 编译出的符号对不上，链接时就会报"无法解析的外部符号"。

**双缓冲防闪烁**：`render_init()` 里 `BeginBatchDraw()`，每帧末 `FlushBatchDraw()`，退出时 `EndBatchDraw()`。不加这段画面会明显抖动，答辩演示时尤其明显。

**画蛇身的正确姿势**：用 `game_foreach_snake()` 一次遍历画完，整体 O(n)；不要写 `for (i = 0; i < len; i++) game_snake_cell(...)`，那是 O(n²)——蛇长 1000 时每帧就是 100 万次遍历。

**中文显示**：`setbkmode(TRANSPARENT)`，否则文字背景是黑块。

### 3.8 实验层 `bench/`

- **`bench.c`**：对比实验程序，不依赖 EasyX，可独立编译运行。它把朴素实现（线性查找、随机重试）和数据结构实现放在同样的输入下各跑一遍，输出报告用的两张数据表。

## 四、游戏功能详解

下面逐个说明玩家能看到的每一项功能，以及它在代码里是怎么实现的。

### 4.1 计分

**表现**：吃到食物加一分，显示在底部信息栏和游戏结束提示里。

**实现**：分数保存在 `Game.score` 里，只在**吃到食物**的那一步加一。判断"这一步是否会吃到食物"是在 `game_update()` 开头做的：

```c
will_eat = (new_head == g->food) ? 1 : 0;
```

吃到时走的分支：

```c
if (will_eat) {
    deque_push_front(g->body, new_head);   /* 蛇头前进，但蛇尾不动 → 长度 +1 */
    occupy_cell(g, new_head);
    g->score++;
    spawn_food(g);                          /* 吃完立刻补一颗新食物 */
}
```

读接口是 `game_score(const Game *g)`。分数不只是给玩家看的，它还是**难度曲线的输入**（见 4.6）。

### 4.2 蛇身长度

**表现**：信息栏里的「长度」，等于当前蛇身节数。

**实现**：直接读队列的 `size` 字段，O(1)，不遍历链表：

```c
int game_snake_len(const Game *g) { return deque_size(g->body); }
```

长度与分数的关系：吃到食物时"头插但不尾删"，长度 +1；正常前进时"头插 + 尾删"，长度不变。开局初始长度为 3（`INIT_SNAKE_LEN`），在地图正中偏左横向摆开，头朝右：

```c
hy = MAP_H / 2;  hx = MAP_W / 2;
for (i = INIT_SNAKE_LEN - 1; i >= 0; i--) {
    Pos cell = POS_MAKE(hx - i, hy);
    deque_push_front(g->body, cell);
    occupy_cell(g, cell);
}
```

### 4.3 步数

**表现**：信息栏里的「步数」，本局累计移动步数。

**实现**：`GameStats.steps`，每成功推进一格加一：

```c
g->stats.steps++;
```

它是"按真实对局逐帧实测"出来的，和下面的碰撞比较一样，都是**如实累加、不事后估算**的统计量。用途之一是和碰撞比较对读（见 4.4），用途之二是给报告提供真实对局量的参照。

### 4.4 碰撞比较 —— 本项目最有特色的一项显示

**表现**：信息栏里的「碰撞比较」，本局碰撞检测累计比较（探测）的节点数。

**为什么要显示它**：C 程序跑得太快，蛇长几百时单次操作不足 1 微秒，`clock()` 的误差极大，甚至会出现"优化版更慢"的假象。而**比较次数是确定的、与蛇长严格成线性关系的**。所以项目把"比较次数"这个指标直接搬到游戏界面上，让复杂度变成一个玩家（和答辩老师）能亲眼看到的数字。

**实现**：每次查询哈希表，都取查询前后 `probes` 的差值累加进去：

```c
static int is_occupied(Game *g, Pos pos)
{
    HashSetStats before = hs_stats(g->occupied);
    int hit = hs_contains(g->occupied, pos);
    HashSetStats after  = hs_stats(g->occupied);
    g->stats.collision_checks += (after.probes - before.probes);
    return hit;
}
```

**怎么用它自检**：正常对局中，这个数会**略大于步数**（多出来的部分就是桶链上的额外探测）。如果它明显是步数的好几倍，说明大量键挤在同一个桶里，该检查哈希函数了。

底部信息栏的这一项和 `bench.c` 实验一是**同一个指标**，区别只在于一个是按真实对局逐帧实测，一个是脱离图形环境批量跑出来的。

### 4.5 食物生成

**表现**：地图上随机出现一个红色方块，吃掉后立刻在别的空格补一个。

**实现**：交给空闲格集合，O(1) 且永不重试：

```c
static int spawn_food(Game *g)
{
    if (deque_size(g->body) >= POS_COUNT) return ERR_EMPTY;  /* 蛇填满地图，无处可放 */
    return fp_pick_random(g->pool, &g->food);
}
```

配套维护是：蛇头移到某格 → `fp_remove()`；蛇尾离开某格 → `fp_add()`。开局和重开时 `fp_reset()` 把全部 1600 格标记为空闲。

### 4.6 难度曲线（自动加速）

**表现**：吃得越多，蛇跑得越快，但不会快到无法操作。

**实现**：三个常量定义在 `main.c`：

```c
#define STEP_MS_INITIAL  150   /* 初始每格耗时（毫秒） */
#define STEP_MS_MIN       60   /* 最快不低于这个值 */
#define STEP_MS_DECREASE   8   /* 每吃到一个食物，间隔缩短这么多 */
```

每推进完一步后按当前分数重算间隔：

```c
step_ms = STEP_MS_INITIAL - game_score(g) * STEP_MS_DECREASE;
if (step_ms < STEP_MS_MIN) step_ms = STEP_MS_MIN;
```

即 150ms 起步，每得 1 分减少 8ms，最快到 60ms 封顶；重开时重置回 150ms。这个"随时间收紧"的机制是贪吃蛇的标准做法，也是很好的报告素材——它是一个**用常数和一次线性计算描述的策略**，不需要任何额外数据结构。

### 4.7 转向与禁止反向前进

**表现**：方向键或 `W` `A` `S` `D` 改变行进方向。

**实现**：`game_set_direction()` 先判断是否与当前方向相反，相反就直接忽略并返回 `ERR`，无副作用：

```c
static int is_opposite(Direction a, Direction b)
{
    return (a == DIR_UP    && b == DIR_DOWN)  ||
           (a == DIR_DOWN  && b == DIR_UP)    ||
           (a == DIR_LEFT  && b == DIR_RIGHT) ||
           (a == DIR_RIGHT && b == DIR_LEFT);
}
```

这道校验是防止"蛇原地掉头、下一帧撞到自己脖子"的关键。只允许在 `GS_READY` 和 `GS_RUNNING` 两个状态下改变方向。

> ⚠ 这个校验目前有一个边界情况尚未处理好，详见第六节。

### 4.8 四种游戏状态：开始 / 暂停 / 继续

**表现**：窗口中部会居中提示当前状态——"按空格开始" / "已暂停" / "游戏结束 得分 N 按 R 重开"。

**实现**：用 `GameState` 枚举管理四个状态：

```c
typedef enum {
    GS_READY = 0,   /* 等待开始 */
    GS_RUNNING,     /* 运行中 */
    GS_PAUSED,      /* 暂停 */
    GS_OVER         /* 结束 */
} GameState;
```

空格键的行为是**按状态分派**的：

```c
if (key_pressed_once(VK_SPACE, &was_space)) {
    if (game_state(g) == GS_READY) {
        game_start(g);              /* 等待开始 → 开跑 */
    } else {
        game_toggle_pause(g);       /* 运行中 → 暂停；暂停中 → 继续 */
    }
}
```

`game_toggle_pause()` 只在 `GS_RUNNING` 和 `GS_PAUSED` 之间来回切换，其他状态下调用返回当前状态、不做改变。主循环里也只在 `GS_RUNNING` 时才推进逻辑，所以暂停期间蛇是真正静止的，不是"画面上不动、后台还在走"。

### 4.9 重开（R 键）

**表现**：按 `R` 重开一局。

**实现**：`game_reset()` 把一切恢复到初始状态，包括：

1. 清空三个结构：`deque_clear()` / `hs_clear()` / `fp_reset()`
2. 重新摆出长度为 3 的初始蛇（头朝右），并逐格 `occupy_cell()`
3. `dir = DIR_RIGHT`、`score = 0`、`state = GS_READY`
4. 统计量清零：`collision_checks`、`steps`，以及哈希表和空闲格的内部计数器
5. 生成第一颗食物（若地图已满则退化到备用坐标）

主循环里还要把难度曲线一起复位，否则上一局的高分会让新局一开始就是最快速度：

```c
if (key_pressed_once('R', &was_r)) {
    game_reset(g);
    step_ms = STEP_MS_INITIAL;   /* 速度也重置 */
}
```

**注意一个设计选择**：重开后的状态是 `GS_READY` 而不是直接 `GS_RUNNING`，即玩家需要再按一次空格才开始。这样玩家有时间调整。

### 4.10 退出（ESC）

**表现**：按 `ESC` 关闭窗口退出程序。

**实现**：主循环最开头读一次，命中就 `break` 跳出主循环，然后按顺序收尾：

```c
render_close();      /* EndBatchDraw + closegraph */
game_destroy(g);     /* 释放 deque / hashset / foodpool 三个结构 */
```

`game_destroy()` 会依次销毁三个结构并释放 `Game` 本身；`deque_destroy()`、`hs_destroy()`、`fp_destroy()` 都做了"传入 NULL 也安全"的处理，所以即使某个结构创建失败也能安全退出。

### 4.11 界面绘制

四项内容各有独立配色：

| 元素 | 颜色 |
|---|---|
| 背景 | `RGB(24, 26, 32)` |
| 网格线 | `RGB(38, 41, 50)` |
| 蛇头 | `RGB(80, 220, 130)` |
| 蛇身 | `RGB(46, 170, 100)` |
| 食物 | `RGB(240, 90, 90)` |
| 居中提示文字 | `RGB(255, 220, 90)` |
| 信息栏文字 | `RGB(180, 185, 195)` |

每帧的绘制顺序是：清屏 → 画网格 → 画食物 → 画蛇身（一次遍历）→ 画底部信息栏 → 画居中状态提示 → `FlushBatchDraw()`。

蛇头的区分是靠遍历回调里的 `index == 0`：

```c
static void draw_snake_segment(Pos cell, int index, void *ctx)
{
    int left, top, size;
    (void)ctx;
    render_cell_rect(cell, &left, &top, &size);
    setfillcolor(index == 0 ? COLOR_SNAKE_HEAD : COLOR_SNAKE_BODY);
    solidrectangle(left + 1, top + 1, left + size - 2, top + size - 2);
}
```

底部信息栏这一行是四个统计量同框显示的地方：

```c
sprintf(hud, "分数 %d  长度 %d  碰撞比较 %llu  步数 %llu   R重开  ESC退出",
        game_score(g), game_snake_len(g),
        st.collision_checks, st.steps);
```

中文字符串需要先转成宽字符再交给 EasyX 输出，`to_wide()` 负责这个转换（优先按 UTF-8，失败再退回 ANSI），配套还要在工程里加 `/utf-8` 编译选项。

### 4.12 冲撞判定与撞墙

**表现**：撞到边界墙或撞到自己身体即游戏结束。

**撞墙**：在算新蛇头位置时顺带判断越界，越界直接返回 `ERR`：

```c
if (x < 0 || x >= MAP_W || y < 0 || y >= MAP_H) return ERR;
```

**撞自己**：查哈希集合。这里有一个**极易写错**的细节——如果这一步会吃到食物，蛇尾不动，撞到尾要算撞；如果不吃食物，蛇尾会让出来，此时"撞到当前尾巴所在格"其实是安全的。所以判定时要排除掉本步将要移除的尾节点：

```c
will_eat = (new_head == g->food) ? 1 : 0;
deque_back(g->body, &tail);                 /* 先记下当前蛇尾 */

hit = is_occupied(g, new_head);
if (hit && !(!will_eat && new_head == tail)) {   /* 撞上，且不是"尾巴正要让开"的情形 */
    g->state = GS_OVER;
    return ERR;
}
```

不管哪种撞法，结果都是把状态置为 `GS_OVER` 并返回 `ERR`，主循环下一帧渲染出"游戏结束"提示。

## 五、数据流：走一步里发生了什么

把功能串起来看，`game_update()` 一次典型调用（没吃到食物）的顺序是：

1. 按当前方向算出新蛇头格子；越界则撞墙结束。
2. 判断这一步是否会吃到食物（`new_head == food`）。
3. 记下当前蛇尾格子。
4. 查哈希集合判断新蛇头是否撞到自己（排除"尾巴正要让开"的情形）。
5. 不吃食物：`pop_back` 让出蛇尾 → `release_cell`（哈希表删、空闲格归还）→ `push_front` 占新头 → `occupy_cell`（哈希表插、空闲格移除）。
6. 吃到食物：`push_front` 不删尾 → `occupy_cell` 新头 → `score++` → `spawn_food` 重新取一颗食物。
7. `steps++`。

可以看到，**一份坐标数据在每一步里要同步更新三个结构**，这也是把 `occupy_cell` / `release_cell` 抽成统一入口的原因。

## 六、已知问题

**快速连续转向会导致蛇撞死自己（已复现，尚未修复）。**

现象：蛇向右行进时，在同一个步进间隔内先后按下「上」和「左」，两次 `game_set_direction` 都返回 `OK`，下一次 `game_update` 立即返回 `ERR`，蛇撞到自己的脖子。

根因：`game_set_direction()` 用 `is_opposite(g->dir, d)` 做校验，而 `g->dir` 是"当前方向"而不是"上一步实际执行过的方向"。一步还没走完，连按两个键会把 `g->dir` 改两次——先由 RIGHT 改成 UP，再因为 `is_opposite(UP, LEFT)` 为假而改成 LEFT。此时 `g->dir = LEFT`，但蛇的真实朝向仍是 RIGHT，下一步就把蛇头放进了自己的颈部格子。

触发条件不算苛刻：`main.c` 每帧都读键盘，只要两次按键落在同一个步进间隔内（初始 150 毫秒）就都会生效，属于常见的急转弯操作。

修法（设计好、未落地）：给 `Game` 加一个 `pending_dir` 字段，`game_set_direction` 只写入它并改用"上一步真正走的方向"做校验；`game_update` 开头若 `pending_dir` 有效则应用一次并清空。这样无论帧内按多少次键，每步最多生效一次转向。

## 七、其他易踩的坑（可写进报告「调试分析」一节）

1. **撞到自己身体的判定有个易错细节**：见 4.12，判断时须排除本步将要移除的尾节点。
2. **禁止反向前进**：按下与行进方向相反的键要直接忽略并返回 `ERR`，否则蛇会原地掉头，下一帧撞到自己脖子。（注意第六节那个尚未修复的边界情况。）
3. **`game_update()` 的步骤顺序至关重要**：不吃食物时要先让出蛇尾、再占新头，否则走到当前尾格时会在哈希表里重复插入。顺序写错会出现"蛇穿过自己身体"这类玄学 bug。
4. **EasyX 双缓冲防闪烁**：循环外用 `BeginBatchDraw()`，每帧末 `FlushBatchDraw()`，退出时 `EndBatchDraw()`。
5. **不要用 `Sleep()` 控制速度**（会阻塞消息循环和按键检测），用时间戳累加判断。
6. **输入用 `GetAsyncKeyState()`**，不要用阻塞式 `getch()`。
7. **中文显示需 `setbkmode(TRANSPARENT)`**，否则文字背景是黑块。
8. **不要在渲染层循环调用 `game_snake_cell()`** 画蛇，那是 O(n²)，要用 `game_foreach_snake()`。
