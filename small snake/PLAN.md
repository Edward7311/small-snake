## 二、游戏介绍

### 基本玩法

在 40 × 40 的网格地图上操控一条蛇。蛇持续朝当前方向前进，玩家可以转向；吃到食物后蛇身变长、分数加一，并且**移动速度会随分数逐步加快**。撞到边界墙或撞到自己的身体即游戏结束。

地图共 40 × 40 = 1600 格，窗口尺寸 = 40 × 20 像素 + 四周 40 像素留白 + 36 像素信息栏，即 **880 × 916**。

### 操作方式

| 按键 | 作用 |
|---|---|
| 方向键 或 `W` `A` `S` `D` | 转向（与当前行进方向相反的输入会被忽略） |
| 空格 | 未开始时→开始；运行中→暂停；暂停中→继续 |
| `R` | 重开一局 |
| `ESC` | 退出 |

### 界面与状态

游戏有四个状态，由 `GameState` 枚举管理：`GS_READY`（等待开始）、`GS_RUNNING`（运行中）、`GS_PAUSED`（暂停）、`GS_OVER`（结束）。窗口中部会居中提示当前状态（"按空格开始" / "已暂停" / "游戏结束 得分 N 按 R 重开"）。

底部信息栏实时显示四项数据：

- **分数** —— 吃到的食物数
- **长度** —— 当前蛇身节数
- **碰撞比较** —— 本局碰撞检测累计比较的节点数（详见第六节）
- **步数** —— 本局累计移动步数

### 难度曲线

初始每格耗时 150 毫秒；每得 1 分减少 8 毫秒，最快不低于 60 毫秒。计时用 `GetTickCount64()` 累加时间戳实现，**不使用 `Sleep()` 控制节奏**——`Sleep()` 会阻塞消息循环导致按键失灵，主循环里只在每帧末尾 `Sleep(1)` 让出 CPU。

### 画面

用 EasyX 的双缓冲机制（`BeginBatchDraw` / `FlushBatchDraw` / `EndBatchDraw`）绘制，避免闪烁。蛇头、蛇身、食物、网格、文字各有独立配色。

## 三、用到了哪些数据结构

贪吃蛇的基础版本其实只有"蛇身用链表还是数组"这一个数据结构点，撑不起 30 分报告 + 30 分答辩。所以本项目的思路是：**把游戏往复杂里做一点点，每加一个真实机制，就多一个数据结构的战场。**

游戏逻辑中实际采用三个数据结构：

| 游戏模块 | 朴素做法的问题 | 采用的数据结构 | 复杂度对比 |
|---|---|---|---|
| 蛇身移动 | 数组整体搬移，每步 O(n) | **双端队列**（双向链表） | O(n) → O(1) |
| 咬到自己检测 | 遍历整个身体查找 O(n) | **哈希集合**（链地址法） | O(n) → O(1) |
| 食物生成 | 随机取格、撞了重试，蛇越长越慢 | **空闲格集合**（数组 + 下标互指 + 交换删除） | 期望上百次重试 → 恒定 1 次 |

三者的实现细节：

**蛇身 —— 双端队列。** 每步只做"头部插入 + 尾部删除"两个操作，用双向链表实现后都是 O(1)，不需要像数组那样整体搬移。

**碰撞检测 —— 哈希集合。** 哈希函数先用 Murmur / splitmix 风格的 32 位混合把键打散，再对桶数取模。这一步是必要的：格子编号 `pos = y * 40 + x` 相邻只差 1，如果直接写 `key % 桶数`，当桶数与 `MAP_W = 40` 有公因子时，同一列的格子会被整列撞进同一个桶。装载因子超过 0.75（3/4）时桶数翻倍并重新散列，均摊插入仍是 O(1)。碰撞检测查询走的就是这张表，平均每次查询约 1 次比较，且不随蛇长变化。

**食物生成 —— 空闲格集合。** 用数组加"下标互指"（`cells[]` 存格子号、`slot[]` 存该格子在数组中的位置）实现 O(1) 的删除，删除时用交换删除法补洞。从这个集合里随机取一个位置，**永远一次命中，不需要重试**。

> 游戏逻辑中只保留了上述优化实现。作为对比基准的朴素写法（线性查找、随机重试）保留在独立的实验程序 `bench/bench.c` 中，两者互不干扰。

### 贯穿全项目的一个设计：坐标只有一种表示法

二维坐标 `(x, y)` 压缩成一维整数 `pos = y * MAP_W + x`（定义在 `common.h`）。这个整数**同时**是蛇身链表里存的值、哈希表的键、空闲格表的下标——三处共用同一表示，省掉一层映射，避免坐标对不上导致的隐蔽 bug。

## 五、接口设计约定

以下约定贯穿全部头文件，报告第一部分可以直接引用。

**1. 返回值统一。** 成功返回 `OK`(0)，失败返回负数并区分原因：`ERR`(-1)、`ERR_NOTFOUND`(-2)、`ERR_DUPLICATE`(-3)、`ERR_EMPTY`(-4)。全部定义在 `common.h`。

**2. 多返回值走出参指针。** 形如 `int deque_pop_front(Deque *dq, Pos *out);`——状态码 + 出参返回被删的值。不用全局变量传值。

**3. 坐标只有一种表示法。** 一律通过 `common.h` 的宏操作，不在别处写 `y * 40 + x` 这类魔数。

**4. 只读查询与修改分离。** 渲染层拿到的永远是 `const Game *`，只能调 `game_state()`、`game_snake_len()` 这类 get 接口。

**5. 遍历接口要一次遍历。** `game_foreach_snake(g, fn, ctx)` 整体 O(n)；而 `game_snake_cell(g, index, out)` 每次调用都要从头遍历链表，本身是 O(n)，只能偶尔取一节用。**渲染层画蛇必须用前者**，否则会写成 O(n²)——蛇长 1000 时每帧就是 100 万次遍历。

**6. 统计计数器如实累加，不事后估算。** `HashSetStats.probes`（哈希累计探测次数）、`FoodPool.attempts`（累计取格次数）、`GameStats.collision_checks` / `steps` 都是 `bench.c` 出数据的源头，答辩被追问时要站得住。

**7. 所有头文件包 `extern "C"`。** 因为 `render.cpp` 是 C++ 而其余是 C，不加这层保护会在链接期报"无法解析的外部符号"。详见第七节。

## 六、实测数据

实验程序 `bench/bench.c` 不依赖 EasyX，可独立编译运行。它把朴素实现和数据结构实现放在同样的输入下各跑一遍，输出下面两张表——**直接抄进报告「调试分析 - 效率分析」一节**。

### 为什么用"比较次数"而不是只报耗时

C 跑得太快，蛇长几百时单次操作不足 1 微秒，`clock()` 的误差极大，甚至会出现"优化版更慢"的假象。而"比较次数"是确定的、与蛇长严格成线性关系的。所以两个指标都打印，报告里**以次数为主、耗时为辅**。

### 实验一：碰撞检测

每组发起 200,000 次查询。

| 蛇长 | 朴素比较次数 | 哈希比较次数 | 朴素每次查询 | 哈希每次查询 |
|---|---|---|---|---|
| 100 | 20,000,000 | 80,664 | 100.0 次 | 0.403 次 |
| 400 | 80,000,000 | 116,290 | 400.0 次 | 0.581 次 |
| 800 | 160,000,000 | 159,826 | 800.0 次 | 0.799 次 |
| 1600 | 320,000,000 | 238,490 | 1600.0 次 | 1.192 次 |

上限取 1600 是有依据的：地图共 40 × 40 = 1600 格，蛇身不可能超过格子总数，这就是真实场景下的最大值。

> 口径说明：朴素版的比较次数是**按最坏情况算出来的**（`n × 查询次数`），哈希版的探测次数是**实测的**。

### 实验二：食物生成

每组重复 100,000 次。

| 地图填充率 | 朴素平均尝试次数 | 优化平均尝试次数 | 朴素最大尝试次数 |
|---|---|---|---|
| 10% | 1.11 | 1.00 | 6 |
| 50% | 2.00 | 1.00 | 20 |
| 80% | 4.98 | 1.00 | 58 |
| 90% | 10.01 | 1.00 | 134 |
| 95% | 20.02 | 1.00 | 235 |
| 99% | 99.72 | 1.00 | 1152 |

填充率 = 蛇身占地图总格数的比例，蛇越长填充率越高。填充率 10% 时朴素版只多试一点点，感觉不到；到 99% 时平均要试上百次、最坏试了 1152 次，**这正是长蛇卡顿的根源**。优化版始终是 1.00 次，与填充率完全无关——这就是 O(1) 的意思。

### 游戏内的对应指标

底部信息栏的「碰撞比较」与实验一是**同一个指标**，区别只在于它是按真实对局逐帧实测出来的：蛇每走一步查一次哈希表，每查一次就如实累加。正常对局中它会略大于步数（多出来的部分就是桶链上的额外探测）。可以拿它当自检：如果它明显是步数的好几倍，说明大量键挤在同一个桶里，该检查哈希函数了。

### ⚠ EasyX 只能用 C++

EasyX 的 `graphics.h` 内含 `#error "EasyX is only for C++"`，**不能用 C 编译器编译**。因此 `render.c` 已改名为 **`render.cpp`**，工程里其余模块保持 `.c`。一个工程里 C 和 C++ 混编是完全正常的。

**因而所有头文件必须包 `extern "C"`：**

```c
#ifdef __cplusplus
extern "C" {
#endif
    /* ... 声明 ... */
#ifdef __cplusplus
}   /* extern "C" */
#endif
```

C++ 编译器会对函数名做 name mangling，C 编译器不做，两边符号对不上就会链接失败。已对全部 6 个头文件添加此保护，并实测验证（C 编译 `.c` + C++ 编译 `.cpp` 链接后成功运行）。

## 九、已知问题

**快速连续转向会导致蛇撞死自己（已复现，尚未修复）。**

现象：蛇向右行进时，在同一个步进间隔内先后按下「上」和「左」，两次 `game_set_direction` 都返回 `OK`，下一次 `game_update` 立即返回 `ERR`，蛇撞到自己的脖子。

根因：`game_set_direction()` 用 `is_opposite(g->dir, d)` 做校验，而 `g->dir` 是"当前方向"而不是"上一步实际执行过的方向"。一步还没走完，连按两个键会把 `g->dir` 改两次——先由 RIGHT 改成 UP，再因为 `is_opposite(UP, LEFT)` 为假而改成 LEFT。此时 `g->dir = LEFT`，但蛇的真实朝向仍是 RIGHT，下一步就把蛇头放进了自己的颈部格子。

触发条件不算苛刻：`main.c` 每帧都读键盘，只要两次按键落在同一个步进间隔内（初始 150 毫秒）就都会生效，属于常见的急转弯操作。

修法（设计好、未落地）：给 `Game` 加一个 `pending_dir` 字段，`game_set_direction` 只写入它并改用"上一步真正走的方向"做校验；`game_update` 开头若 `pending_dir` 有效则应用一次并清空。这样无论帧内按多少次键，每步最多生效一次转向。

> 注：`game.h` 里该函数的注释本就写明这个校验是"防止蛇原地掉头撞到自己脖子"的关键，修好后这条注释才算真正成立。

## 十、报告写作参考

### "效率分析"一节的论证链模板

每一段都按这个链条写，这既是报告的骨架，也是答辩时的答问逻辑：

> 这个模块要做什么、数据量多大 → 不用数据结构、写最直白的循环会怎样（变慢？还是根本写不出来？） → 为什么选这个而不选另一个（插入/查找/内存代价对比） → **实测数据**（跑 `bench.exe` 得到）

理论复杂度只是起点，有实测数据才叫工程能力。

### 容易踩的坑（可写进"调试分析"一节）

1. **撞到自己身体的判定有个易错细节**：如果这一步会吃到食物，蛇尾不动，撞到尾要算撞；如果不吃食物，蛇尾会让出来，此时"撞到当前尾巴所在格"其实是安全的。最稳妥的做法是判断时排除掉本步将要移除的尾节点。
2. **禁止反向前进**：按下与行进方向相反的键要直接忽略并返回 `ERR`，否则蛇会原地掉头，下一帧撞到自己脖子。（注意第九节那个尚未修复的边界情况。）
3. **`game_update()` 的步骤顺序至关重要**：不吃食物时要**先让出蛇尾、再占新头**，否则走到当前尾格时会在哈希表里重复插入。顺序写错会出现"蛇穿过自己身体"这类玄学 bug。
4. **EasyX 双缓冲防闪烁**：循环外用 `BeginBatchDraw()`，每帧末 `FlushBatchDraw()`，退出时 `EndBatchDraw()`。不加画面会明显抖动，答辩演示时尤其明显。
5. **不要用 `Sleep()` 控制速度**（会阻塞消息循环和按键检测），用时间戳累加判断。
6. **输入用 `GetAsyncKeyState()`**，不要用阻塞式 `getch()`。
7. **中文显示需 `setbkmode(TRANSPARENT)`**，否则文字背景是黑块。
